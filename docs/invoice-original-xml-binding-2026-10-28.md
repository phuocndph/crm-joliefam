# Explicit target binding of original Viettel XML — 2026-10-28

## Problem and proof boundary

The real downloaded ZIP parses as one invoice, four lines and two files. Its XML uses the TT78 legal model digit and unpadded SHDon; the API canonical invoice uses a registered template/version and padded invoiceNumber. The old target import rejects their different text identities. Removing that check alone would let ordinary ingest create a second canonical invoice, so the global natural key, parser and generic identity matching remain unchanged.

Official Viettel v2.54 documents invoiceType (TT78 enum 1–6) separately from templateCode. Binding uses the explicit API invoiceType value exactly equal to XML KHMSHDon. It never infers the XML legal model from a template prefix. This phase supports only an explicitly selected, issued normal outgoing Viettel invoice (state1/adjustmentType1/spec2.54), source VIETTEL_FILE, one parsed VN_HDON_XML invoice and exactly one XML file. Other states/models/ambiguous documents fail closed. Ordinary exact natural-identity target imports keep their existing path.

The server owns the proof. It checks current API provider ID/source_identity against the canonical snapshot, explicit raw seller/buyer tax codes, registered template, series, currency, full invoiceNo and numeric invoiceNumber; API numeric padding may differ but the original fullNo suffix must be the exact unpadded positive number. FullNo is read, not manufactured for an API request. XML/canonical/current API and explicit API raw totals must agree exactly across all three header amounts. Date checks reuse normalized API business date and canonical invoiceBusinessDate plus the adapter issueDateStr first-ten-character path, or the same milliseconds+Vietnam-offset fallback when that source field is absent. No naive slicing of a canonical UTC timestamp is used.

Company-wide collision checks include records hidden by owner ACL and return only a generic 409: competing canonical seller/series/numeric number across templates; observation XML identity/hash or equivalent legal number on another invoice; any staged file checksum attached elsewhere or unassigned. Existing natural-key/source-identity collisions remain checked during ingest. Later independent XML import under any source label is rejected if its XML identity/hash already belongs to a canonical invoice in a different namespace. This prevents duplicate canonical invoices after binding without expanding global identity matching. Exact-natural ordinary XML imports retain their previous behavior.

## Staging, commit and immutable data

The existing preview transaction holds the company lock and loads the selected target. New binding requires both import and files ACL. The server stages proof kind, target/revision, latest API observation ID/hash, XML byte checksum, stable input-value hash, both identities, explicit invoiceType/fullNo, closed checks and a fingerprint. A private stable serialization handles JSONB object-key ordering only inside this proof; it never changes parsed XML values or the existing observation hash algorithm.

The UI shows both identity representations, explicit model/type evidence and XML checksum; it states the signature/legal limitation and requires an explicit checkbox and the existing reason. Commit accepts confirm_original_binding:true only as acknowledgement, never as a proof. It holds the company/job/target locks, rechecks current ACL/revision/latest API observation and collisions, regenerates the proof and compares the staged fingerprint. A process-owned WeakMap context authorizes only the already-validated target for this exact input; JSON from a client cannot manufacture it. Existing expiry/idempotency semantics remain, and committed replays recheck target import/files ACL before returning their receipt.

Ingest appends the original parsed XML payload, source_identity, observation hash and extracted source evidence to the selected canonical invoice. The only suppressed false identity differences are intentional invoice_number/template_code representation differences under the trusted context. Status/legal unknown, existing XML discrepancies, names/addresses or line differences still retain the needs_review path. Canonical snapshot, legal identity, lines, status, money, links and allocations are never replaced. Original XML/PDF bytes are checksum-verified and deduplicated using existing file storage. BIND_ORIGINAL_XML audit records proof and reason; metadata lives only in staged job/audit/receipt, not injected into XML payload/raw or source identity. Transaction failure rolls back database changes.

## Validation and limits

Implementer read-only smoke used the actual downloaded ZIP with a mocked in-memory database interface: accepted explicit model/identity, immutable XML input, stable fingerprint after reordered keys, denied forged context and wrong model. ZIP SHA256 C37321C9D9082F09F406804C53B4F8D8DAFF3603A6669051956DE40891863FF7; XML SHA256 8FBD2014286F0A88260E19467F93256705E7607D271ACF1E0D51C9FE51E9D6A1. This does not claim an operational import occurred.

Required implementer gates: app/server TypeScript, scoped ESLint, app/server builds and diff-check. Tester owns real-byte isolated API acceptance, replay/different-source dedupe, ACL/hidden collisions, stale revision/latest source, wrong raw/model/date/money/state, immutable bytes/payload/canonical values, rollback and full regressions after the frozen manifest. Parent owns runtime activation, operational backup and eventual actual target import plus mobile proof.

No migration, provider call, credential access, operational DB/auth/grant mutation, runtime restart, commit/push/deployment, broad natural-key normalization, XML parser change or automatic provider-file protocol change is included. Imported XML parsing/file presence does not verify signatures, legal validity or financial review. This is a new bounded original-binding phase with at most two independent review/test repair cycles.

## Accepted repair cycle 1 — V2

- Independent XML guard also compares bounded positive numeric SHDon for the same original XML seller/model/series, so changing zero padding and byte hash cannot create a second invoice after binding. This remains rejection rather than an implicit attachment; exact-natural ordinary XML behavior is unchanged.
- API publication template must be nonempty, trimmed and at most 20 characters, exactly equal to canonical template. Latest API evidence must have source VIETTEL and canonical source_kind must be VIETTEL, in addition to the provider/spec/id checks.
- Company-wide historical collision lookup now fetches scalar candidate fields only, using XML identity/hash, provider/source ID, raw invoiceId, full invoiceNo aliases or seller/series candidates as SQL predicates. Any same provider ID or fullNo on another invoice blocks binding even if that historical payload has conflicting legal fields. Owner-hidden rows still participate without exposing their identifiers.
- Bound XML status unknown is kept as unknown in immutable payload and its review warning remains; it does not add a false canonical status-change conflict. Other statuses still use the prior conflict check. Identity-mismatch guidance requires source/target reconciliation and no longer suggests an independent-import bypass.

Only server/invoice-original-binding.ts and server/invoice-workspace.ts change from frozen V1. No API shape, frontend, parser, migration, file protocol or operational data change is introduced. TypeScript/lint/build/diff checks and independent fixed-manifest review/tests are repeated. Repair-cycle budget used: 1 of 2.
